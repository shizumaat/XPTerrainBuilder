# #1472 CYVR — `Overlay input is mixed-dimension` inside `frame_entry.enter` (lane l1472)

## Attribution
Traceback (l1208's CYVR build, `cc413ba64`): `door_wells.read_family` →
`obj8.above_grade_footprint` → `obj8._place` → `frame_entry.enter` line 187,
the `make_valid` of the repair loop (step (c)).

Mechanism, reproduced headless: the placement affine + 1 mm snap collapses a
tiny part of a resource's MultiPolygon footprint to zero area (all its
vertices round onto one grid point, or onto one line).  The snapped
MultiPolygon is invalid, so `enter` hands it to `make_valid`.  GEOS repairs
each part, gets a POINT/LINE for the collapsed one and a polygon for the
others, and its union of the repaired parts refuses the mix:
`IllegalArgumentException: Overlay input is mixed-dimension`.
Fuzz (60,000 random 2-3-part MultiPolygons on a 0.5 grid, GEOS 3.13.1):
21 raise; **0** raise once the zero-area parts are dropped first.

Same class as #1136 / #1147 (an area's overlay must be an area,
`geom/parts.areal_part`): a repair operand of an area must be its areal part.

## Rule
`enter` already keeps only polygonal parts above one grid cell (steps (d),
(e)).  That same extraction now runs BEFORE every `make_valid` too: a part
that carries no area is dropped before the repair instead of after it.
Nothing that survives changes — (d)/(e) dropped those parts anyway.
`obj8_clip._union_rings`' local repair of clipped rings keeps the areal
part of each repaired ring (`geom/parts.areal_part`) before the union.

## Acceptance
- Synthetic twin: a MultiPolygon with a collapsed part through `enter`
  is red on main (raises), green after; the polygonal result keeps the live
  part's area.
