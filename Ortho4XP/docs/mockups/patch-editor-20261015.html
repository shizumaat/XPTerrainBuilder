Patch editor: design and plan

When the map is zoomed in on one airport, draw the patch the engine will build. In Edit mode you can select, move, delete and insert nodes, change their elevation, and undo. Saving writes a manual patch, and the engine already prefers a manual patch over the auto patch. A 3D preview shows the terrain with the patch applied, and you can orbit it while you edit.

3D preview

A separate window, opened with the toolbar's 3D button or ⌘3, that shows the same airport as the map. You can place it next to the map or on a second display. Drag to orbit, scroll to zoom, and ⌥-drag to pan. The nodes selected on the map are shown here too, and each edit appears in the next frame. The installed airport pack's buildings stand on the terrain as grey massing models, so you can find areas to adjust by the buildings around them.

Where they differAt the edges of the patch, where the mesh stage blends the patch into the terrain, and wherever the mesh stage simplifies triangles. That is why the live view is labelled "Preview".
Buildings sit as X-Plane draws themEach object stands on the terrain at its anchor point, plus its authored height. With an edited patch, object re-seating is off, so lowering the ground under a hangar leaves it floating in the preview, just as it would in the sim. Moving parts (jetway animations) are left out.

Architecture

The engine owns the files; each front end owns the interaction. Reading and writing patches, the staleness stamps and the pack outlines are handled by JSONL commands, so the Mac and Qt apps get the same behaviour. Selection, dragging and undo happen locally in each app, because a round trip to the engine on every drag frame would be too slow.

New engine commands (protocol 1.10, reply only; no new event classes, so the event-name wire hazard is not touched)

  • patch_load {tile, icao} returns the source (auto / manual), path, nodes [id, lat, lon, alt_abs?], ways [id, refs, tags], bounding box and stale. It reads the same file include_patches would pick, so the map shows what the engine will build. Hand-made JOSM patches load too; nodes without alt_abs show "elevation from the mesh".
  • patch_list {tile} returns the airports in the tile that have a patch and their bounding boxes, so the map knows where patches exist.
  • patch_save {tile, icao, nodes, ways} writes <ICAO>_edited.patch.osm with all tags kept and the auto patch's freshness stamps recorded as o4_edited_from_*. It writes atomically (temp file, then rename).
  • patch_revert {tile, icao} renames the edited file to .disabled.
  • pack_outlines {tile, icao} returns the apt.dat pavement and boundary rings (Bézier curves flattened) and the object footprints the engine already reads for re-seating.
  • terrain_sample {tile, icao, bbox, spacing_m} returns an elevation grid as base64 float32. It reuses auto_patch_v2/airport/dem.load_dem, so it reads the same base and insets the airport solve reads. It never downloads: if the DEM is missing, it replies with an error that says so.
  • mesh_crop {tile, bbox} returns the triangles of the built Data<tile>.mesh that fall inside the box. It reuses the parser in auto_patch/mesh_sampler.py.
  • pack_objects {tile, icao, bbox} returns each distinct object's solid, non-animated triangles once, plus its placements (lon, lat, heading, height mode). It reuses the pack DSF placement reader (auto_patch_v2/airport/dsf.py) and the OBJ8 parser with library resolution (airport/obj8.py, ResourceCache). It reads the caches only: a pack whose DSF dump or library index isn't cached is reported, never regenerated. Facades are drawn as their outline raised to the facade's height.

Edit operations: one specification, two implementations, one twin test

The operations are move, set elevation, offset elevation, delete nodes and split an edge. They live in o4_engine/patch_edit.py, which the Qt app imports directly, and in SceneryKit/PatchDocument.swift. A shared JSON fixture of operation sequences and expected results runs in both pytest and swift test, so the two cannot drift.

Mac files

  • SceneryKit/PatchDocument.swift: the model, the edit operations and a spatial grid for hit-testing
  • XPTerrainBuilder/PatchEditModel.swift: the ObservableObject that holds the document, selection, mode and undo registration
  • XPTerrainBuilder/PatchOverlay.swift: drawing and gestures, called from MapCanvasView with a few lines, so that file does not grow
  • XPTerrainBuilder/PatchInspector.swift: the Patch box, added to BuildPane below Activity
  • OrthoEngineClient.swift: the eight command wrappers
  • SceneryKit/PatchTriangulator.swift: ear-clipping triangulation with hole support, per shape (patch shapes carry gap_interior_ring holes)
  • XPTerrainBuilder/TerrainPreviewWindow.swift: a separate window holding a SceneKit view with an orbit camera. Each patch shape is its own geometry, so an edit rebuilds a single buffer. It also holds the terrain grid, the imagery drape from the map's cached tiles, and the pack buildings as shared-geometry clones, so one hangar model is stored once no matter how many times it is placed.

Performance

The largest patch on disk is 12k nodes (KPDX), and OTHH-class patches may be several times that. Drawing is culled to the viewport. Nodes are drawn only when they are far enough apart on screen. During a drag only the moved nodes' shapes are rebuilt, and the patch draws into its own layer so the base map isn't redrawn every frame.

Plan

L1
Engine: commands and edit operations. patch_list/load/save/revert, patch_edit.py, the twin fixture, and tests for load → save → load identity and for include_patches picking the edited file and turning re-seating off. Opus lane, runs first.
L2
Mac: read-only render. Client wrappers, PatchDocument, the overlay and the View-mode Patch box. Can start in parallel with L1, using a fixture reply.
L3
Mac: Edit mode. Select, multi-select, drag, delete, insert, elevation field, offset, undo/redo, save, revert, the unsaved-edits prompt and Rebuild tile. Comes after L2.
L4
Pack reference outlines. pack_outlines in the engine and drawing in both apps. Runs independently once L1's command scaffolding has landed.
L5
Qt parity. The same overlay and panel in O4_Qt_Map.py using QUndoStack, calling patch_edit.py directly. Comes after L3, so it copies the settled behaviour.
L6
3D preview (Mac). Takes two rounds. 6a: terrain_sample, PatchTriangulator (with a twin test against the engine's own triangulation of a fixture shape), and TerrainPreviewView with an orbit camera, a vertical exaggeration control, live updates from PatchEditModel and selection highlighting. 6b: pack_objects and the buildings, which re-seat on the preview surface as you edit. 6c: the imagery drape, mesh_crop and the "Last build" option. 6a starts once L2 has landed PatchDocument, and runs alongside L3. The preview reads the edit model and never writes to it, so L3 and L6 touch different files.
L7
3D preview (Qt). The same view in the Qt app, using pyqtgraph's OpenGL widget. Its sampling and triangulation come straight from the engine modules in Python. Comes after L5 and 6a.
✓
Closing test. On one built airport: edit a few nodes, save, rebuild the tile, then confirm that the build log says "using the MANUAL patch" and that the DSF reads the new elevations at those points. No sweep is needed, because auto patches are unchanged unless an edited file exists.

Not in v1

  • Grade-law checking of edits (your choice). The census can be added on save later.
  • Generating a patch without a tile build
  • A delta overlay that re-applies edits to new auto patches
  • Drawing new shapes, editing tags, splitting or joining ways
  • An elevation colour ramp
  • Selecting or dragging nodes in the 3D view. All editing stays in the 2D map, and the 3D view is for looking.
  • Rebuilding the exact mesh live. "Last build" refreshes only after a tile rebuild.

Owner answers, 2026-10-15

  1. Zero-violation acceptance. A tile whose airport uses an edited patch reports grade violations without failing, and the result is labelled "user-edited". L1 checks how a build treats a manual patch today and makes it behave this way.
  2. File name. <ICAO>_edited.patch.osm, the convention the engine already recognises.
  3. Object re-seating. Stays off while the edited patch is in use. Added: the 3D preview shows the pack's buildings, to help find areas to adjust (L6, round 6b).
  4. 3D placement. A separate window only.
  5. Preview extent. The patch's bounding box plus 500 m, at 5 m spacing.
