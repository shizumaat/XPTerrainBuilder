## 0. Verdict first

1. **A spatial relevance cull does not work at OTHH.** The emitted patch covers 14.1 km² (1,508 graded faces); 1,073 of the 1,175 plan members (166,137 of 173,912 parts) have a part box touching a graded face, 1,144 within 200 m, and 710 members (146,419 parts) have at least one FOOT on a face (measured from `OTHH.rebake.json` × `OTHH.graded.json`). The pack IS the airport. "The parts that matter" has to be decided by CONSUMER, not by distance.

2. **By consumer, two whole classes of object-stage work provably never touch the patch:**
   - the **rebake plan** (`pipeline/build.py:1276-1300`) runs AFTER `write_patch` (`wall["emit"]` closes at :1273) and writes only `<ICAO>.rebake.json` + a report line — ~195 s cold after perfC (the extension's narrow pass, 172.9 s profiled, is uncached cold);
   - the **basin rim diagnostics** (`planar/basins.py:558` `_rim_open`, `:655` `rim_wall_report`) — the ONLY readers of the at-grade LINEWORK in the basin pass; both feed note strings (`rim_note` :560, `:657-664`), a report. 315 of 355 profiled basin seconds; ≈145 s plain pass 1 after perfB memoises pass 2.
   Both need an OWNER ruling (the plan's clock is inside the 600 s; the rim report was ordered "reported, never a refusal", `structures.toml:560`).

3. **Exact (byte-identical by construction) items reach ≈ 960 s cold / ≈ 540 s warm** (from the post-A–F baseline I reconstruct at ≈ 1,510 cold / ≈ 830 warm). **600 s cold needs the two rulings AND the planar-stage parallelism (§4): ≈ 530 cold.** Without any ruling the exact+parallel plan lands at ≈ 790 cold. The ruling that buys most is the rebake plan leaving the patch build (−195 cold; also removes 282 s from every warm build on a tree without perfC's extension cache). **< 300 s cold is not reachable with this plan**; < 300 WARM is plausible (≈ 440 estimated) — see §6.

4. HECA (711 cold) has neither ruling's work in it (rebake plan 0.38 s, no basins). It goes under 600 on the pooled partition + vectorised constraints alone (≈ 480 estimated); its own next sink is the staged active-set solve (stage 1: 113 s, 310 rounds, "HARD SET NOT SETTLED").

5. One correction to prof362: the extension does not re-add "6,235 parts". It places **27,690** parts (95 members: 93 jetways of 5 resources + 2 `tunnel1.obj`, 247–353 parts each; the profile's own `ndarray.all 27,690 calls` is one per new part). 173,912 − 167,677 = 6,235 is the NET after `filtered()` dropped 7 terrain-adapted members' parts. 213,917 of the 214,332 contacts touching jetway parts are jetway–jetway (intra-member, kept by RULINGS 2026-09-10i (1) at `contact.py:909/923`). ## 4. Parallelism — the second lever

Facts: `src/auto_patch_v2` has no pool (grep). The airport build already runs inside `concurrent.futures.ProcessPoolExecutor(mp_context=spawn)` (`auto_patch/driver.py:1135,1167`) whose workers are NOT daemonic (cf workers may spawn children; `multiprocessing.Pool` workers may not). `Ortho4XP.py:20` calls `freeze_support`. The airport pool already takes ALL logical cores (`config.parallel_airports_worker_count :1307`), so a nested pool must take a core BUDGET (`O4_PARALLEL_AIRPORTS_N`-aware: inner = max(1, cores // active airport workers)) or the app's tile (OTHH+OTBD+OTBH in +25+051) oversubscribes — prof362 §5 measured 2.46× contention already. The DEM must not be re-shipped per task: sample what each task needs in the parent (anchor/corner/centroid z) and ship arrays, or use the driver's initializer pattern once per worker. Geometry must NOT cross the pipe back: `PlacedPart.pts/tris` for 167k parts is the whole placed pack; workers return plan rows (box, centroid, area, feet, rings, height — the `Part` fields) and per-pair verdict records; the narrow pass runs in the workers that own the parts, counterpart geometry re-placed from the worker's own `ResourceCache` (parse is 24 s for the whole pack) or shared via `multiprocessing.shared_memory` (spawn- and freeze-safe). New pool module = one new file in `auto_patch_v2/airport` (or `geom`), imports at module top (frozen engine: function-level third-party imports are invisible to the freeze; a module named only in a string needs `hiddenimports` in BOTH `.spec` files).

Ranked:
1. **Exact, merge in input order** (byte-identical by construction): per-member `placed_parts` (86.5), per-resource `_build_member` (82), per-placement witnesses (44 + parse), per-cluster `cluster_topology` (52), per-family wall corridors (139 families; sorted order kept), door-well witness pass (J, 40 of 55), the four classification-free planar reads concurrently (door wells ∥ sunken roads ∥ wall corridors ∥ tunnel/plates/basins: ≈ 55+32+70 → ≈ 75 on 3 workers), pass 2 concurrent with pass-1 constraints (≈ 130 ∥ 71).
2. **Exact with a replay proof**: the narrow contact pass (§2 row 4a): verdicts are per pair and order-free; the spanning subset is reproduced by replaying the recorded verdicts through today's loop. Needs the twin to show identical `contacts` on a captured pair set (`test_v2partextend.py` has the machinery).
3. **Not poolable as is**: `_derive_groups` (reads the DEM through `airport.dem.z`, 8 s — leave it), the arrangement (one GEOS subdivision), the solve.

Estimated cold savings on 5 cores after pickling overhead: pack stage ≈ 540 → ≈ 150 (−390: placing/members/witness/topology pooled ≈ −200, narrow all-pairs parallel ≈ −60 load / −130 extension if R1 is not taken, lazy profiles −40); planar reads ≈ −100; pass 2 overlap ≈ −70.
